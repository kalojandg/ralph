# Ralph Plan — авторство на task board

RALPH_ROOT = директорията на ralph репото (на тази машина: `D:\Downloads\monk\ralph`; на непозната — намери директорията, съдържаща `ralph-swarm.ps1`, или питай). Пълните референции живеят в `RALPH_ROOT/ralph reference/` — при съмнение чети `parallel-swarm-reference.md` Част 2 и `tasks-and-progress-reference.md`.

## Процедура

### 1. Разузнаване (ЗАДЪЛЖИТЕЛНО преди писане)
- Прочети `RALPH_ROOT/ralph reference/project reference/repos.json` → кое репо, mainBranch, verify команди, structure reference.
- Прочети structure reference документа на целевото репо (ако липсва → първо `/ralph-setup`).
- Прочети реалния код, който тасковете ще пипат: точни имена на функции/файлове/DOM id-та правят стъпките изпълними. При голям проект (много сървиси/зони) — fan-out: по един Explore агент на зона, събери картите, чак тогава декомпозирай.
- Идентифицирай ОТРОВНИЯ СПИСЪК на репото: споделени файлове (DI/bootstrap, router, locales, package.json, shared types, contracts, солюшън файлове). Те определят соло lane-овете.

### 2. ПАРАЛЕЛИЗЪМ ПО ПОДРАЗБИРАНЕ — мисли в ЗОНИ, не в стъпки

Серийността е ИЗКЛЮЧЕНИЕ, което се доказва — не дефолт. Наративното мислене („първо X,
после Y") ражда линейни board-ове; обърни реда:
1. Първо начертай ЗОНИТЕ НА СОБСТВЕНОСТ (кои файлове/модули са независими острови).
2. Режи работата ПО ЗОНИ — всяка зона = кандидат-lane.
3. Серализирай САМО при доказано: (а) споделен файл, (б) нужда от РЕАЛНИЯ merged код.
   Всяка серализация получава изрично „защо" в notes на таска.

Отключващи техники (прилагай ги, ПРЕДИ да приемеш серийност):
- **Подготвителен SPLIT таск**: серийността идва от монолитен/споделен файл? Първи таск
  разцепва собствеността (модуларизация, токенизация, registry), после ветрило от lanes.
  Цената +1 сериен таск се изплаща при ≥2 отключени lane-а (доказано: shared-inventory).
- **Contract-first**: интерфейсът в кратък соло таск → консуматорите ПАРАЛЕЛНО с мокове;
  dependsOn само ако наистина трябва merged кодът (стъбиране пред секвениране).
- **Новите файлове са безплатен паралелизъм**: таскове, които само СЪЗДАВАТ файлове
  (тестове, нови модули, data файлове) не се бият — вади ги в отделни lanes агресивно.
- **Registry per фича**: нова фича се закача чрез СОБСТВЕН файл, не чрез редакция на общ
  списък — общият файл серализира всичко след него.
- **Cross-repo е винаги паралелен** (отделни gitRoots — конфликт невъзможен).

### 2а. ОДИТ НА ПАРАЛЕЛИЗМА (задължителен, преди да покажеш board-а)
- Всяка ДВОЙКА таскове в една lane: наистина ли споделят файлове/зависимост? Не → раздели.
- Всеки dependsOn: трябва ли merged кодът, или мок + контрактът дословно в двата спека стига?
- Смятай: N таска, L lanes, критичен път K (най-дългата lane/dependsOn верига), макс M
  едновременни агента. Wall-clock ≈ K, НЕ N. **K/N > 0.6 → преструктурирай или обоснови
  всяка брънка** (обикновено липсва split/contract таск).
- ДОКЛАДВАЙ на потребителя: „N таска, L lanes, критичен път K, макс M агента" + списък на
  серализациите с причините им.
- Питай потребителя САМО при истинска развилка (split таск срещу серийност; две валидни
  архитектури с различен паралелизъм). НЕ питай за еднозначно решими от одита неща.

### 2б. Правила за декомпозиция
1. **Разбивай по фичи, не по слоеве.** Един таск = един commit = един merge. Къси таскове — дълголетен branch = конфликт.
2. **Нула файлово застъпване между lanes.** Два таска на един файл → същата lane (ред = редът в масива) или dependsOn. Lane-овете вървят паралелно; вътре в lane — последователно.
3. **`repo` полето е ЗАДЪЛЖИТЕЛНО** на всеки таск (multi-repo fleet — няма безопасен дефолт; липсва → шумен skip).
4. **`files` = glob-ове = зони на собственост**, не списък файлове. Гранулярност по избор: цял сървис = 1 ред (`Services/OrderService/**`). Отровен файл в files → соло lane + dependsOn.
5. **`dependsOn` гейтва на MERGED** (worktree на зависимия се клонира от integration при старта му). Cross-repo dependsOn работи. Цикъл = deadlock.
6. **Поведенческа промяна = спековете се оправят В СЪЩИЯ таск/commit** — иначе гейтът на merge-а е червен по конструкция. Патърн за консолидации: първо АДИТИВЕН таск (новото + негов spec, старото непипнато), после премахващи таскове един по един (всеки чисти своите спекове).
7. **TDD**: RED+GREEN в ЕДИН таск (`tddWorkflow: true`). Характеризационни тестове = документират каквото Е, върху замразен код.
8. **Id-та не се преизползват** (логовете/retry файловете са per id) — номерирай с луфтове по lane (10-те, 20-те…).
9. `description` = git commit message дословно (conventional style). `specRef` сочи секции от structure reference. `notes` носи червените линии и контекста, който агентът иначе няма как да знае.

### 2в. Модел per таск (`model` полето — ЗАДЪЛЖИТЕЛНА преценка при авторство)

Конфигът (`ralph-config.json → models`) мапва tier имена към модели (дефолт: easy=Sonnet,
heavy=Opus, review=Fable). Всеки таск носи `"model": "easy" | "heavy"` (или конкретен
`claude-*` id за изключения); липсва → heavy. Board-ът сочи TIER, не модел — при квотна
криза потребителят сменя стойностите в конфига, board-ът не се пипа.

**Лакмусът: чия е мисловната работа?** Ако ТИ (авторът) си я свършил — диагнозата е
готова, рецептата е в notes, файловете са изброени — таскът е **easy**. Ако агентът
трябва да я СВЪРШИ — да открие причина, да проектира slice, да съгласува контракт —
таскът е **heavy**.

- **easy** (по дефолт Sonnet): UI полиш/рестайл по съществуващи токени; wiring/“врати"
  (линкове, montage на готови компоненти); локали/i18n ключове; характеризационни
  тестове върху замразен код; фиксове с ГОТОВА диагноза + точен фикс в notes; docs
  таскове; механични преименувания/изтривания с изброени файлове.
- **heavy** (по дефолт Opus): нов slice/фича (handler + типове + тестове); промени по
  schema/contracts; работа през много файлове с интеграционни решения; бъг БЕЗ готова
  причина (агентът диагностицира); таскове с очакван escalate/conflict потенциал;
  финалният таск на дълга lane (reconcile/интеграция); всичко с Testcontainers/инфра.
- **review** tier НЕ се пише в таскове — той е finishing конфиг (review+fix агентите).

Правила: (1) при съмнение → heavy — изгорелият retry бюджет струва повече от ценовата
разлика; (2) в одита по §2а докладвай и разбивката easy/heavy; (3) МОДЕЛНА ЕСКАЛАЦИЯ:
харнесът сам вдига таска едно стъпало по easy → heavy → review (Fable), когато стигне
escalate прага (escalate_after изгорени fail retry-та — същият момент, в който се вдига
и files scope-ът): easy → heavy; heavy → review модела като последен шанс (Fable гори
отделния Fable джоб на Max — почти безплатен за swarm квотата). Това е предпазната
мрежа на tier преценката: смей да маркираш easy — сгрешена преценка се самокоригира
с цената на 2 евтини опита, не с провален таск; а heavy таск в задънена улица получава
най-силния модел + вдигнатия scope точно преди терминален провал.

### 3. Verify стратегия (гейтът)
- **Per-task `verify` масив** за междинните таскове: прицелен subset `["npm test -- <spec-filter> critical-path"]` (playwright филтрира по подниз). БЕЗ `npm ci`, ако таскът не пипа package.json.
- **Финалният таск на всяка lane — БЕЗ verify override** → пълният repo гейт е задната мрежа.
- Във филтъра само спекове, които СЪЩЕСТВУВАТ след таска (изтрит спек във филтъра = playwright error = фалшиво червено).
- Провери, че пълният suite се събира в `swarm.verify_timeout_min` (мери с baseline; виж /ralph-setup).

### 4. Механика на board-а
- `tasks.json` = чист JSON масив, редът в масива = ред на изпълнение в lane.
- ⚠ PowerShell капан при програмно append: пиши с `ConvertTo-Json -InputObject $array -Depth 16` (pipeline-ът `$arr | ConvertTo-Json` увива в `{value, Count}` и чупи board-а).
- Валидация преди пускане: уникални id-та; всички dependsOn таргети съществуват; всеки таск има repo; files на различни lanes не се пресичат; описанията са commit-готови.

### 5. ПОТВЪРЖДЕНИЕ НА ИНТЕГРАЦИОННИЯ КЛОН (задължително, ПРЕДИ старт)
Оркестраторът merge-ва в `repos.json → mainBranch` на всяко репо — БЕЗ да пита. Затова
ТИ питаш потребителя, за всяко репо в board-а:

1. Провери реалността: `git -C <location> rev-parse --abbrev-ref HEAD` + `mainBranch` от repos.json.
2. Кажи ИЗРИЧНО: „Репо <X>: в момента сте на клон '<current>'; агентите ще merge-ват в
   '<mainBranch>'. Да?"
   - **„Да"** → продължавай със сегашната логика.
   - **„Не"** → питай КОЙ клон; създай го и го checkout-ни (`git checkout -b <нов>` от
     текущия), ОБНОВИ `repos.json → mainBranch` на това репо към новия клон, потвърди
     двете. (И двете стъпки са нужни: worktree-ите тръгват ОТ mainBranch и merge-ват В него,
     а merge проверката изисква главният checkout да е НА него.)
3. ⚠ Board към `main`/`master`/`develop` (прод/интеграционни клонове на екип) — САМО след
   изрично „да". Никога по подразбиране.
4. Напомни финала: след зелен board интеграционният клон се преглежда и merge-ва към прод
   клона ОТ ЧОВЕКА, после `mainBranch` в repos.json се връща на старата стойност.

### 5а. Преди старт
Останалият чеклист е в `/ralph-setup` (зелен baseline на ексклузивен порт, чист integration branch и т.н.). Не пускай board върху непроверена база — фосилите се плащат с retry бюджети.
